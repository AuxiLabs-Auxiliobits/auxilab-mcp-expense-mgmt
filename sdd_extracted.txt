1. Introduction
1.1 Purpose of the SDD
This  System  Design  Document  (SDD)  establishes  a  formal,  production-grade  architectural  blueprint  for
ExpenseOps, an AI-powered expense management server natively built on top of Anthropic's Model Context
Protocol  (MCP).  This  document  defines  the  structural  patterns,  API  schemas,  data  topologies,  rule  engine
workflows, and security frameworks necessary to transition ExpenseOps from concept into a scalable, enterprise-
ready fintech automation platform.
1.2 Project Overview
ExpenseOps transforms legacy, human-in-the-loop expense compliance processes into an autonomous workflow
orchestrator. Natively utilizing MCP, the platform abstracts complex tasks—such as optical character recognition
(OCR),  multi-dimensional  line-item  parsing,  policy  enforcement,  structural  risk/fraud  scoring,  and  real-time
dashboard updating—into single, reusable tools. These tools are dynamically discoverable and invocable by Large
Language Model (LLM) agents, internal microservices, and enterprise automation runners.
1.3 Intended Audience
Solution Architects: To evaluate system compliance with enterprise security, isolation barriers, and
governance standards.
Backend & Platform Engineers: To serve as a definitive implementation guide for codebase construction,
schema generation, and routing logic.
Enterprise Software Teams: To facilitate seamless tool discovery, tool integration, and agent-driven corporate
workflow authoring.
1.4 Technical Scope
The scope of this document covers the implementation details of the core Python-based server layer using
FastMCP , the deterministic business rules engine, statistical risk/fraud calculations, local-to-cloud transactional
database configurations, UI layout semantics, and fallback procedures for flaky AI model dependencies. Legacy
integrations (such as SAP/Workday pipelines) are addressed via abstract data transfer definitions.
1.5 Engineering Objectives
The platform is architected to achieve extreme reliability in data capture, deterministic transparency in policy
execution, low-latency API response times, clear audit trails, and strict separation between non-deterministic AI
tasks and immutable compliance rules.

2. System Overview
2.1 Overall Platform Behavior
ExpenseOps  functions  as  a  dual-mode  engine:  it  serves  traditional  requests  via  standard  REST  APIs  while
simultaneously operating as an active Model Context Protocol (MCP) server. When a user submits an expense via
the frontend or an automated enterprise receipt sink, the data flows into a multi-tiered ingestion pipe. The system
unifies raw text capture, multi-stage layout extraction, and predictive LLM token structuring into a single context-
aware pass.
2.2 Finance Automation Objectives
Traditional finance departments suffer from human error, delayed processing windows, and high operational costs.
ExpenseOps replaces physical manual matching with autonomous validations. By executing continuous vector-
distance calculations for duplicates and parsing multi-line receipts against complex cross-border tax codes, the
system processes 95% of standard receipts without human intervention, escalating only clear structural anomalies
to human reviewers.
2.3 MCP-Native Architecture
Unlike standard monolithic wrappers, ExpenseOps treats the MCP specification as its primary protocol surface. The
server registers its capabilities (tools, prompts, and resources) with an upstream MCP Host (such as a corporate
proxy or an LLM client). This permits structural agent-driven exploration: an AI agent reading an email body can
independently call ExpenseOps' tools to extract a receipt, validate it against corporate travel policy, flag exceptions,
and present a structured summary directly to an executive.
2.4 Reusable Tooling Concept
Every internal subsystem is exposed as an atomic, stateless MCP tool. These tools are designed with zero cross-
tool tight coupling; they rely entirely on uniform input JSON schemas and return well-formatted structural strings or
JSON objects. This modular design ensures that the exact same validation engine used by a web frontend button
can be utilized by an autonomous Slack bot or a nightly cron worker.
2.5 AI-Assisted Workflow Orchestration
The platform distinguishes between the  deterministic engine (which enforces static items like budget limits,
currencies,  and  roles)  and  the  cognitive  engine (which  classifies  abstract  categories,  handles  language
translation, and extracts line items from distorted receipt captures). Workflow orchestration uses the LLM to make
intelligent routing decisions (e.g., "This looks like an out-of-policy entertainment expense; trigger the high-risk
workflow path") while using code blocks to execute financial validations.

5. Why MCP Architecture?
5.1 What is Model Context Protocol?
The Model Context Protocol (MCP) is an open-standard communication protocol designed by Anthropic to govern
how AI clients securely discover, inspect, and execute capabilities across external microservices. It explicitly models
capabilities into three core interfaces: Tools (executable operations), Resources (readable state data layers), and
Prompts (pre-constructed contextual strategies).
5.2 Architectural Selection Rationale
Traditional expense platforms use brittle REST APIs that require frontends or orchestrators to be completely
rewritten every time a field changes. ExpenseOps selects MCP to build an abstract, future-proof layer where an
LLM agent doesn't need custom pre-compiled backend bindings. If the agent needs to analyze compliance, it reads
the server's capabilities description, inspects the parameter schemas, and invokes the tool natively using JSON-
RPC, transforming the software engine into a dynamic runtime environment.

7.1 Expense Policy & Business Rules Engine
Purpose: Validates  line-item  parameters  against  structured  organizational  guidelines  to  determine  policy
compliance.
Inputs: Transaction detail map (amount, currency, category, role, location).
Outputs: Validation response object containing policy status (PASS, EXCEPTION), flag arrays, and specific error
codes.
Processing  Logic: Loads  the  active  JSON  policy  configuration.  Evaluates  the  transaction  against  defined
categorical constraints, role spending caps, and local geographic allowances.
Edge Cases & Fallbacks: If the currency field does not match the corporate baseline, the engine safely triggers an
internal currency conversion workflow. If conversion rates are missing, the claim is flagged as an exception and held
for review.
7.2 Duplicate Detection & Risk Scoring Engine
Purpose: Identifies double-billing and malicious duplication trends across corporate historical transaction logs.
Inputs: Target transaction payload, comparison history buffer.
Outputs: Floating-point duplicate probability rating [0.00 - 1.00], structural risk indicator markers.
Processing  Logic: Executes  a  exact-match  sweep  across  amount/date  fields,  combined  with  a  normalized
Levenshtein distance check on merchant names. A multi-factor mathematical formula determines the final risk
score.
Performance Considerations: Limit lookback query scopes to a maximum 180-day window using composite
indexes to prevent high database memory overhead.
7.3 Receipt Parsing & OCR Processing Engine
Purpose: Processes uploaded document files to extract structured financial data arrays.
Inputs: Binary raw file buffer (Image / PDF format).
Outputs: Structured document details (merchant name, date string, total amount, line items array).
Processing Logic: Extracts raw text characters using localized OCR rendering. Passes the resulting text blocks to
an LLM context window using structured instructions to enforce strict Pydantic parsing maps.
Error Handling: If the extracted text quality drops below an acceptable structural threshold, the system triggers an
alternative regex match strategy. If both fail, the claim is routed for human remediation with a low-confidence tag.

9. Exception Handling Architecture
9.1 Structural Hierarchy and Escalation Logic
When validation failures occur, claims are systematically categorized into structured severity tiers rather than being
rejected  outright.  This  allows  the  system  to  route  exceptions  along  appropriate  remediation  paths  based  on
organizational impact.
9.2 Specialized Override Frameworks
To accommodate edge cases without compromising core control structures, the system includes dedicated override
pathways:
VIP Executive Overrides: Automatically processes business travel claims submitted by C-Suite executives,
skipping low-level managerial queues and routing directly to dedicated executive finance controllers.
Geographic / Location Overrides: Adjusts maximum spending allowances automatically based on destination
country indicators to account for local market conditions and fluctuating inflation profiles.
Conflict Resolution Rules: If a claim triggers conflicting system rules, the engine resolves the impasse by
enforcing the most restrictive constraint by default to safeguard organizational budgets.

10. Risk Scoring System Design
10.1 Weighted Framework and Core Formula
The Risk Engine computes a unified composite risk metric,  R, for every submitted claim. This calculation maps
across multiple individual risk elements, using specific weighting coefficients (wi) to produce a normalized final
score from 0 to 100:
R = min(100, Σ (Si × wi) + Pduplicate)
Where the key evaluation components are defined as:
Samount: Percentage variance exceeding standard category averages (w = 0.35).
Stime: Suspicious submission window indicator, such as off-hours weekend timestamps (w = 0.15).
Scategory: Historical risk rating of the assigned accounting category (w = 0.20).
Pduplicate: Statistical probability matrix score indicating double-submission risk (w = 0.30).

10.3 Reference Metric Calculation Example
Consider an input claim for an Entertainment expense that exceeds typical category spend averages by 40%
(Samount = 40), occurs at 2:00 AM on a Saturday night (Stime = 80), falls within a high-risk category baseline
(Scategory = 50), and shows a minor potential duplicate string match proximity (Pduplicate = 20). The calculation is
performed as follows:
R = (40 × 0.35) + (80 × 0.15) + (50 × 0.20) + (20 × 0.30)
R = 14.00 + 12.00 + 10.00 + 6.00 = 42.00
The resulting composite score of  42.00 places the claim into the  Medium Risk tier, systematically routing it for
review rather than auto-approval.

11. AI Integration Architecture
11.1 Balancing Cognitive and Deterministic Logic
ExpenseOps enforces a strict separation between cognitive interpretation and financial validation. The system
never allows an LLM to decide whether a claim is legally valid or to modify currency calculations. Instead, the AI
serves as an isolation layer that reads unstructured source files to produce structured data blocks, which are then
evaluated by deterministic business rule validation engines.

11.3 Confidence Scoring and Graceful Degradation Tiers
Downstream LLM responses include a token confidence score generated by analyzing log-probability values. If the

    # Standard compliance simulation logic block
